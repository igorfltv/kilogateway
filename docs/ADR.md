# Решения

1. **Самостоятельная реализация.** Backend Kilo cloud в закреплённом commit — OCVSAL 1.0. Его код не переносился. Сохранена копия лицензии исключительно архитектурного референса. Право тестировать fork не означает право production использования этого fork. Новый проект не объявляет коммерческие права на upstream backend.
2. **Python backend, TypeScript plugin.** FastAPI, httpx, SQLAlchemy async/asyncpg, PostgreSQL и Alembic; uv.lock и requirements с hashes. TypeScript нужен для фактического Kilo plugin API. Node LTS используется для build/helper, сам Kilo содержит собственный Bun runtime.
3. **Четыре credentials.** Keycloak access JWT проверяется только gateway exchange. Opaque `cg_gc_<public-id>.<random-256-bit-secret>` выдаётся CLI; сервер хранит HMAC-SHA256 с внешним hashing key. Пользовательский inference key хранится AES-256-GCM и передаётся только inference adapter. Management credential применяется только Management API. Ни один из этих четырёх секретов не подменяет другой.
4. **Device Flow.** Public client `kilo-cli`, без client secret, OIDC discovery с canonical issuer/endpoint origin validation. Native auth hook возвращает `key`; Kilo stores API auth. Никакого выдуманного logout hook, автопродления API key или поддержки IDE.
5. **Авторизация.** RS256 JWT: signature/JWKS rotation, `iss`, `aud=code-ai-api`, exp/iat, непустой sub, `azp=kilo-cli`, `typ=Bearer`, роли `invoke` и `issue-credential`. ID token отвергается. Tenant/issuer/subject — устойчивая identity; email не используется. JWKS cache 5 минут, неизвестный kid вызывает rate-bounded refresh. Устаревшие ключи не принимаются без успешной проверки подписи.
6. **Статус.** Перед выдачей/запросами проверяется локальный suspend. Keycloak Admin API читает enabled и effective realm roles с bounded freshness 1..60 секунд (default 30; local fixture 2). Снимок датируется началом network check, не концом. По истечении свежести ошибка IdP закрывает доступ. Это проверка при обращении; уже открытый inference не обещается принудительно остановить после изменения роли.
7. **Идемпотентность.** Exchange сериализуется PostgreSQL advisory lock по principal. `(principal, Idempotency-Key)` связан с device/client hash. 5 минут хранится зашифрованный ответ с тем же key; изменённое тело — 409. После TTL — 409, ciphertext удаляет worker, tombstone остаётся. Сеть может повторить тот же exchange без выпуска бесконтрольного количества credentials. Для нового сознательного входа создаётся новый idempotency key.
8. **Broker.** PostgreSQL advisory lock по principal/provider действует между репликами. Уникальный partial index допускает только один active key. Перед внешним POST атомарно сохраняются operation UUID/label и budget allocation. Provider create не считается идемпотентным; label не объявляется уникальным у провайдера. На ambiguity состояние остаётся started/uncertain, новые create блокируются. Worker ищет **все** exact-label совпадения, отзывает их; пустой результат не доказывает отсутствие ещё выполняющегося create. Тогда нужна операторская сверка. Бюджет не освобождается автоматически при неоднозначном исходе.
9. **Ротация.** Дождаться отсутствия in-flight requests → создать и зашифровать новый → транзакционно перевести старый в revoke_pending, новый active и записать durable revoke job → удалить старый с retries. DB failure после create вызывает compensating revoke; durable operation остаётся recovery evidence при невозможности записи/cleanup. Suspend немедленно отзывает gateway credentials и ставит active upstream keys в durable revoke очередь. Удаление одного device credential общий key не удаляет.
10. **Деньги и quotas.** `provider_allocated` principal монотонно суммирует полный limit каждого поколения, даже если фактически потрачено меньше. Новый login переиспользует key и не меняет allocation. Ротация потребляет следующую долю оставшегося principal allocation. Автоматического восстановления неистраченного лимита и обнуления бюджета нет. Это консервативная граница суммы выданных provider limits; точный денежный hard cap по неполному usage не обещается. Отдельно PostgreSQL атомарно ограничивает request rate/concurrency и суточные/общие accounting units. Reservation = UTF-8 JSON bytes + 1024 overhead + output limit; это консервативные единицы, не точная токенизация. Reservation сохраняется при ошибке/disconnect/restart; provider-reported token counts/cost записываются с provenance. Валидный больший reported usage увеличивает charge. В MVP reservation не возвращается даже при меньшем usage.
11. **Inference.** Только Chat Completions, строгий top-level allowlist; alias преобразуется в серверный model ID. Никаких пользовательских URL/routing headers или внешнего fallback. Только явно построенные headers. Один HTTP attempt, без автоматического inference retry. SSE читается по событиям, максимум 64 KiB на frame, без полного накопления ответа. Downstream send управляет backpressure. Ошибки до headers — JSON, после — безопасный SSE error + DONE. HTTP disconnect закрывает upstream response; остановка реальных вычислений/биллинга зависит от upstream.
12. **Production.** Corporate adapter намеренно fail-closed. Local Compose и fake endpoints — development. AES backend реализует SecretStore protocol; production KMS/Vault backend необходимо подключить к этому интерфейсу и проверить до допуска. Административный API использует отдельный secret и закрытый ingress; public machine API никогда не отправляет на HTML login.

Состояния provider credential: `active → revoke_pending → revoked`; intent/state provisioning вынесены в `provisioning_operations: started → complete | uncertain | failed`. `uncertain` не превращается в новую попытку create без reconciliation. Durable jobs содержат только FK на credential, без plaintext secret. Restart с orphan проверен отдельными fault-injection tests.
